LoopFormer

TL;DR

I wanted to see if a tiny language model could follow a graph one step at a time, then keep going for much longer than it had practiced. I looped the middle layers of Qwen2.5-0.5B-Instruct and trained each loop to predict the next node. After several revisions, the executor follows every step correctly on 96.89% of 1,350 unseen graphs at 256 steps, after training on at most twelve.

A separate learned timer stops it at exactly the requested loop for every tested count from 1–256, with 97.78% correct final answers at 256. I gave the timer a counting structure and numerical training labels through 63. The result is specific to fixed-format graphs with 26 states, so longer paths revisit nodes. The experiments below show what failed along the way and how I separated execution from stopping.

Introduction

It is no secret that Large Language Models have gotten really good. Throughout the last few years, the capabilities of models in complex reasoning tasks such as coding and mathematics have improved significantly, coming along with leaps in pre-training and post-training techniques. And innovations are not just at the frontier, smaller models can now also be trained to perform comparably when trained on specific, specialized tasks.

One of the recent advances in this area has been the introduction of the Recurrent Looped Transformer architecture. The idea is that we can get more reasoning performance out of a language model by allowing it to loop over some selected layers multiple times before providing the outputs. I found this idea quite interesting and wanted to investigate if this technique could be used to train a smaller language model to perform a specific, repetitive, procedural task where each loop of the recurrent layers can represent a single step towards solving the overall problem.

The Task

I wanted a task built from simple steps that a tiny language model could learn to repeat. The problem should also be something that can be programmatically solved to make it easier to benchmark and evaluate the model's performance later. After some thought, I settled on a pointer-following task, which ends up being somewhat similar to traversing a cyclical directed graph when solved programmatically.

Let's define a node in this graph as a point that is assigned a letter of the alphabet - say (A) represents node A. Nodes in this graph are connected by edges, with each one pointing to just one other node for simplicity's sake. Let (A, B) denote the edge going from node A to node B. To add complexity to this task, we use repetitions. Given a set of rules (which represent a graph), we define N to be a number of steps to take from a designated starting node. In future, I may refer to N as "depth" or "task depth". The model is expected to follow the edges of the graph for N steps and return the node that it ends up at.

For example, given the following rules:

  • (A, B)
  • (B, C)
  • (C, A)
and a starting node of A with N = 4, the model should follow the transitions A → B → C → A → B and return B as the final node.

This task has some limitations. For starters, since I used single-lettered nodes, the number of unique nodes (and subsequently, rules) is limited to 26. Secondly, having just one edge per node makes the task quite straightforward, that is another layer of complexity that can be added later. Some ideas to add complexities to those can be to use double-lettered nodes, or to add another parameter such as a color to each edge to make the task more challenging. However, my selected task serves as a good starting point to test the Recurrent Looped Transformer architecture and see if a tiny model can learn to reason through this task.

Data

Given the simple, structured nature of this task, I could generate a large amount of synthetic data rather easily. I previously described the structure of the data required for this task. For the initial experiments, I sample N+1 distinct letters and connect them into a path of N transitions, using its first letter as the starting node. I then assign random destinations to all remaining nodes and shuffle the order of the rules. Each graph contains all 26 nodes, but its requested path never repeats a node. Requested depths are balanced across the chosen range (which can be varied). The fixed format also lets me determine the correct outputs (including traces to the final node) programmatically. For reproducibility, I set seeds for all random number generators and generate multiple seeded datasets to evaluate generalizability to unseen graphs and depths.

Note that in later experiments, I change the generator to sample graphs independently of the requested depth, allowing repeated states and cycles. I will describe that change alongside the corresponding model.

Metrics

This task has a few different things that can go wrong. Just knowing that the final answer is wrong does not tell us whether the model followed the wrong edge, lost track after several steps, or stopped too early. I designed the benchmark to help separate these problems. Some measurements only become relevant in later architectures, but I describe them together here.

The full benchmark uses 1,350 graphs across three generation seeds, with requested depths from 1 to 256. That gives us 345,600 graph/count queries per model. The graphs include random functions, permutations, and full 26-state cycles. In random functions, each node's destination is chosen independently. Permutations give every node exactly one incoming edge, while full cycles connect all 26 nodes into a single cycle. This full benchmark suite was introduced later but I have retroactively applied it to the earlier models for comparison. I describe the smaller evaluations used during training alongside each run. Since there are still only 26 nodes, longer runs necessarily revisit nodes.

Does the model get the answer right?

First, I check the answer after exactly N loops, regardless of whether the model wanted to stop earlier. This is forced final accuracy, and it lets us evaluate graph execution separately from stopping. I also check the answer at each intermediate loop, which gives us per-loop accuracy.

Did it take the correct steps to get there?

Getting the final answer right is not enough here. The model could take a wrong step and still end up at the correct node later, especially when the graph has cycles. So I also check whether every intermediate step was correct. This is complete trajectory accuracy: here, just one wrong step makes the whole trajectory a failure.

Where does it start going wrong?

A model that fails immediately has a different problem from one that works for twenty steps before losing track. I record the first incorrect loop and plot how many examples remain correct through each step, called survival. I also measure the fraction of previously correct examples that fail at the next loop—the conditional first-error rate—and the average number of correct steps before failure. These comparisons keep the requested count fixed, since changing the Steps field can also change the model’s behavior.

Does the requested count change the execution?

The correct state at a given loop should depend on the rules and starting node, even if I ask the model to keep going for longer afterward. I compare the same graphs at the same intermediate loop while changing only the requested count. This checks whether the number of steps in the prompt is affecting execution before it should need to stop.

Can it recover after a mistake?

After a wrong prediction, the model might stay wrong or return to the correct path. I track how often predictions are wrong, how long those stretches last, and how often a wrong prediction is followed by a correct one. The correct answer keeps moving through the graph, so recovery means matching the reference at the current step. It does not erase the earlier mistake, and wrong stretches still continuing at the end are marked as unfinished.

What kind of mistake is it making?

At the first error, I check whether the model repeated the previous state, returned to another earlier state, predicted a reachable state it had not visited yet, or predicted a state outside the start node’s reachable path. I assign these categories in that order to avoid counting an error twice. I also check whether its predictions still follow valid graph edges after it loses track. This is decoded transition consistency: the model can follow valid edges while being on the wrong part of the graph.

Is the problem in the recurrent block or in the final readout?

A later architecture lets us predict a letter directly from the recurrent block as well as through the final readout. Comparing these predictions, especially at the first error, tells us whether the two readouts disagree. For example, the direct prediction might be correct while the final readout is wrong. This helps locate a discrepancy, although it does not tell us exactly what the hidden state represents. Earlier architectures do not have this additional readout.

Does it know when to stop?

A model might execute the graph correctly but stop after six steps when we asked for ten. Exact-stop accuracy checks whether its first stop signal occurs at exactly the requested loop. I also separate early, late, and missing stops, and measure how far the signaled stops are from the requested count. The benchmark uses a stop threshold of 0.5 and a safety cap of 272 loops (relevant to later architectures). Reaching that cap without signaling counts as a missing stop.

Is it reading and updating the count correctly?

For the later controllers, I also check the initial count estimate and how the predicted remaining work changes over the loops. The GRU uses an auxiliary numerical readout for this diagnostic; the final timer has a scalar memory that we can inspect directly. I keep these smaller development and controller-only tests separate from the graph benchmark, and compare the numerical estimate with the actual stop signal.

Does the whole system work?

I check the letter returned when execution stops, but the right letter at the wrong time can be a coincidence on a cyclic graph. End-to-end success therefore requires both the correct answer and exact stopping. Strict autonomous success additionally requires every intermediate step to be correct. Breaking outcomes down by answer correctness and stopping correctness helps show which part failed, and missing stops and correct letters reached only at the safety cap remain explicitly marked.

Which problems are harder?

I compare performance across requested depths and graph properties, including graph type, cycle length, the number of steps before entering a cycle, and the number of reachable states. I separate familiar requested counts, held-out counts within the training range, and depths beyond training. Seeing a number in a training prompt is different from being trained to execute that many steps. Each comparison includes example counts as well as success rates.

How much confidence can we have in the comparison?

Testing the same graph at 256 requested depths does not give us 256 independent graphs. To estimate uncertainty, I resample whole graphs within the seed and graph-type groups, keeping their queries together and using the same samples when comparing models. This measures variation across graphs, not across training runs or untested numbers. The later controller-only test through 8,192 steps is reported separately, since it tests stopping without executing the graph.

Baselines

Before changing the architecture, I wanted to see how well the original model could handle this task on its own. This gives me a starting point to compare against when training the recurrent models.

Experiments

I ran three experiments on the same 1,350 graphs at requested counts 1–256, giving us 345,600 queries per experiment.

Just asking Qwen

I used the original Qwen2.5-0.5B-Instruct checkpoint, without any additional training. I gave it three examples at depths 1, 2 and 3, each with its own rule table and final answer, followed by the graph to solve. The prompt asks for just the final letter, without intermediate steps or an explanation. I used Qwen's chat template and greedy decoding, with a maximum of eight output tokens.

I evaluated it on the same full benchmark described above. A response counts as correct only if it is the expected uppercase letter after removing surrounding whitespace. The model can generate any token; answers that do not follow the requested format still count as failures. Since it only returns a final answer, we cannot measure its intermediate trajectory or assign it a recurrent stopping time.

Letting it show its work

Asking for just the answer does not give the model room to write out the steps. So, I gave the unchanged checkpoint three examples that show the intermediate states, and asked it to return every letter along the path, excluding the starting node. The last letter in this sequence is its answer. The model has to generate the steps and decide when to stop on its own. I kept greedy decoding and allowed up to 272 new tokens, enough to write out the longest requested trace.

Training the ordinary model

Next, I fine-tuned all 494 million parameters of the original model to generate these traces, keeping ordinary autoregressive generation. I used the same 36,000 training examples used by the later recurrent executor, with requested counts 1–6, 8, 10 and 12. Counts 7, 9 and 11 are left out as requested lengths, though those positions can still occur inside a longer training trace. Training ran for one epoch, or 2,250 updates, with an effective batch size of 16.

The loss covers every response token, including the end-of-sequence token, but excludes the prompt. During training, the model receives the correct preceding states. During evaluation, it has to continue from its own predictions. I selected update 2,250 using validation loss on the trained counts.

Both trace experiments use the same prompt and generation settings. The direct-answer experiment uses FP32 and an eight-token budget, while the trace experiments use BF16 and 272 tokens. So this is not an isolated test of changing the prompt alone.

Analysis

Full SFT clearly teaches the model something useful: it can generate the entire path and stop correctly at every trained count on this benchmark. The problem is carrying that behavior to unfamiliar requested lengths. The eleven-step example makes this particularly clear, since it follows all eleven transitions correctly and then generates one more. Low training loss and a correct final letter would each miss part of that failure.

This gives us a baseline of what the instruction-tuned model can do, and also what vanilla SFT can bring to the table. It does not show that ordinary transformers cannot solve the task with another recipe. Full SFT also updates many more parameters than the recurrent models, and a generated token is not equivalent to one recurrent loop in compute cost. The recurrent readouts choose among 26 letters, while ordinary generation uses the full vocabulary. The final timer also receives separate numerical supervision through 63, whereas trace SFT uses requested lengths through twelve. These differences mean the comparison cannot isolate the benefit of recurrence alone.

The First Attempt

Model Architecture

For all training experiments, I start with the Qwen2.5-0.5B-Instruct checkpoint; model specs can be found here. Let us call layers 0-5 P, layers 6-17 R, and layers 18-23 C. For this first attempt, I freeze the P and C blocks and only train the LoRA adapters within R, the recurrent block. I take ht at the end of R and feed it back into the input of R for the next step, then ht+1 = R(ht). The output of C is used to generate the final output.

The complete [batch, sequence, 896] P output initializes h0. With R being reapplied to all positions at every loop, representations of rules, start, steps and the answer position are all allowed to evolve together. The original causal mask and RoPE positions are reused. Rank-8 q/v LoRA in R supplies 270,336 trainable parameters. This model must learn to loop over the graph, following the correct path at each step. For this initial experiment, I supply the correct loop count during training and evaluation.

Training

I trained the LoRA adapters on 30,000 synthetic examples, with 5,000 examples at each requested depth ranging from 1 to 6. Each example used a different rule table, with a nonrepeating path through its requested depth. I used an AdamW optimizer with a learning rate of 2e-4 (10 warmup updates, then constant), weight decay was 0. I set the batch size to 4, accumulating gradients over 2 batches (effective batch size of 8). I also clipped gradients to a maximum norm of 1.0. I trained for 1 epoch (3,750 steps).

The training objective was cross-entropy over the 26 possible letter outputs, targeting the correct symbol after exactly t transitions at loop t. I averaged the losses across the requested transitions within each example, then across examples so that each example contributed equally, so a six-step problem did not contribute six times as much loss as a one-step problem. Loss masks remove loops after an example's requested N. Earlier hidden states remain in the autograd graph so that earlier loops can be trained from later losses. Note that while the trainer knows t, N and reference states for labels, it does not feed those labels back into the model. There was no stopping loss in this first attempt.

Every 250 steps, I ran a validation set of 32 examples each at depths 1-8 (256 examples total). This is to measure performance on unseen graphs, and also on unseen depths to see whether the model can generalize to longer paths with just a small set of training depths. Depths 1-6 measured in-distribution performance, while depths 7-8 measured extrapolation.

Analysis

The main result is that the model learns to follow a path through the training lengths, performing very well on lengths 1-6 on unseen graphs. It also generalizes to lengths 7-8 (though not as well), but performance drops sharply after that.

Looking into what the first-error actually is can be informative for understanding the model's behavior. The first errors are fairly evenly spread between the failure modes of repeated state, another earlier state, a later reachable state, or a state outside the reachable path from the starting node. This seems like the model is simply learning to output any letter past the training depth rather than learning to follow the graph structure. The error categories alone do not prove that the choices are random, but the sharp loss of complete trajectories shows that the execution is no longer reliable.

My analysis of the type of graphs the model struggles with shows that out of the graph structures, the model gets some answers right on random functions. However, complete trajectory accuracy is low across all three families at 12 steps, and by 32 steps only random functions retain any complete successes. No family retains a complete trajectory at length 256. With so few complete successes at the longer depths, I do not think there is a reliable graph-specific behavior to build on here.

There is also a part of the task this first version never had to learn: when to finish. I supplied the loop budget myself, so before revising the recurrence I wanted to see what happened when the model had to make that decision too.

The First Revision

Model Architecture

For this version, I wanted the model to decide when to stop by using the requested steps already present in the prompt. I kept the same P, R and C split, with the original Qwen weights frozen and rank-8 q/v LoRA adapters in R.

The first change was to add a small stopping head that reads the answer-position hidden state after each R loop. It uses LayerNorm, a 896-to-128 linear layer, GELU, and a final scalar output converted to a stop probability by a sigmoid. It has no separate memory or external counter, so it has to learn progress from the hidden state. During inference, the model stops at the first probability of at least 0.5 and returns the letter decoded through C, with a fixed safety cap if no stop is predicted.

In this version, the entire sequence still changes on every loop. I train the stopping head jointly with the adapters, bringing the total to 387,073 trainable parameters. This means learning when to stop can also change how R learns to follow the graph. Neither the stop prediction nor the decoded letter is fed back into R.

Training

I used the same data, optimizer settings, training budget and validation schedule as the first attempt.

The new part of training was the stopping loss. I kept the letter cross-entropy at every requested step and added binary cross-entropy with a weight of 0.1: continue before N, stop at N. To keep the single stop label from being outweighed by the continue labels, I gave the mean continue loss and final stop loss equal weight. For one-step examples, the stopping objective only contains the stop term, since there are no preceding continue steps. Training still runs through the requested depth even if the head predicts an early stop, with no supervision after that depth.

Architecture 3a

A Fixed Prompt

Model Architecture

In the previous versions, the entire hidden state changes each time we loop through R, including the representations of the rules, start and requested steps. I wanted to keep that prompt information fixed and let only the answer position change as the model follows the graph.

P still encodes the full prompt once. At each R layer, I keep the prompt representations from the first pass and reuse them on later loops. This memory is fixed within a rollout, but it is recomputed for each forward pass and remains in the autograd graph during training.

I kept the same adapters and stopping head as the previous version. The requested steps are still present in the prompt. I changed where the model can write, without adding a separate counter or controller memory.

A Whole New Architecture

Model Architecture

So far, the models have learned to step through the graphs and stop at the right time for training depths, but execution accuracy drops sharply on longer unseen rollouts. This seems to be a mix of a data problem and also a model problem - something about the architecture itself does not lend itself to generalization. This calls for a revision of the whole architecture itself, and a new data recipe.

The old architecture was possibly doing too much - both the evaluation of the next step, and the stopping decision were being jointly trained and possibly interfering with one another. I thought it would be best to separate the two tasks. On one side, let's have a part of the model that is solely responsible for evaluating the next step. And on the other side, let's also have another part of the model that takes up the task of deciding when to stop. I call these the executor and the controller respectively.

To separate these jobs, I also changed what each part gets to see. I remove the Steps line from the executor's prompt, leaving it with the rules and starting node. The controller gets P's representation of the full prompt, including Steps, and can observe the executor's hidden state at each loop. Both versions of the prompt pass through the same frozen P before looping. The controller still has to learn to read the requested count from the prompt; it is not given a separate numerical count or loop index.

The Executor

The executor is equivalent to what was previously just the R block. It takes in the hidden state from P or from itself at the previous step, and outputs the next hidden state. One subtle problem with the previous architecture was that R’s output was fed directly back into its input, without a separate learned mapping between the two. This could cause the hidden state to drift in scale as we loop, making each new input less like the output from P that R was originally trained to receive. To address this possibility, I added a re-entry bridge that normalizes the output hidden state to the initial P state’s scale, then applies a learned gain and projection before feeding it back into R. The first loop skips this bridge.

The Controller

The controller is a separate GRU with its own 128-dimensional memory. The controller's memory is initialized from the output of P through a learned projection. Then at each loop, it takes the output from the executor as its input and updates its own memory to make a continue/stop decision.

As in 3a, the prompt memory stays fixed and only the answer-position state changes across loops.

This gives R direct supervision on the current state as well as supervision through C. Neither readout is fed back into the next loop. The controller was trained alongside the executor with the stopping loss, but that loss now updates only the controller.

Analysis

This is the first version where more loops continue to produce useful execution across the full benchmark. The failure pattern has changed too. Most paths stay correct all the way through, and when the model is wrong, its decoded transitions usually still follow valid edges. That is different from the earlier versions losing the path near the training limit and rarely making valid transitions afterward. It does not tell us exactly what the hidden state represents, but the behavior is much closer to the repeated operation I wanted.

Several things changed together: the count-free prompt, the bridge, full training of R, direct supervision and cyclic training graphs. I cannot give one of them all the credit from this run. What we can separate clearly now is the remaining stopping failure, since the controller cannot change the executor’s state and the stopping loss no longer updates the executor.

The numerical diagnostic also shows that errors can start before the first loop, when the GRU’s initial memory is read as the requested count. Later updates and the stop decision add their own errors, so more accurate initialization alone is not guaranteed to fix it. For this task, though, the controller has a very specific job: count the requested transitions. That made me want to try a simpler memory and update rule instead of asking the GRU to learn everything at once.

The Missing Piece

Model Architecture

At this point, I had an executor that could keep stepping through the graph correctly (most of the time), but the controller was still struggling to decide when to stop on longer requests. I thought the GRU might be doing more than this task needed. We already know what completion means here - just take the requested number of steps. So I kept the executor frozen and replaced the controller with a much simpler learned timer.

A simpler memory

Instead of a 128-dimensional GRU memory, the controller now keeps a single number representing how much work is left. At each loop, a small learned update multiplies this number by a scalar and adds a bias: mt = a · mt-1 + b. A separate learned readout uses the updated value to decide whether to continue or stop. The same update is reused at every loop. I do not set the update to subtract one; the coefficients have to be learned from the remaining-work targets.

Reading the requested count

The timer also needs a starting value. I take the raw digit tokens from the Steps field and use their frozen token embeddings directly instead of passing the full prompt through P for the controller. One shared learned projection maps each digit embedding to a scalar, and a learned accumulation gain combines these values from left to right. Using the same weights at every position gives the reader a way to compose longer numbers from the digits it has already seen. The code extracts the digit tokens, but does not convert the text into an integer and hand that value to the controller.

The executor still sees only the rules and starting node. The timer now reads only the requested count, and no longer uses the executor's hidden state. This means it can learn when the requested work should end, but cannot tell whether the executor has made a mistake. I am giving the controller a specific counting structure here, rather than asking it to discover a general stopping strategy.

Training

I kept the same graph/count panel and 12-loop training limit as the previous controller run. All of the executor weights stayed frozen. The remaining-work targets now supervise the scalar memory directly, while the stopping loss trains only the stop readout. The timer runs on its own predictions during training; the correct remaining count is used as a target, never fed back into its memory.

I first trained this scalar controller with a linear reader of the final eight frozen token embeddings in the prompt. I fitted that reader to the training-count labels with least squares and froze it, then trained the countdown and stop readout for 3,000 updates. I used AdamW with a learning rate of 0.01, with the countdown's multiplicative coefficient learning 100 times more slowly. The schedule used 100 warmup updates followed by cosine decay to one tenth of the starting rate. Batch size and validation frequency stayed the same. The same short-count stopping criterion selected update 3,000.

The first reader had separate weights for each token position, which became a problem when digits appeared in positions it had not learned to read. Analysis

The main result here is that I could fix stopping without changing the executor at all. Its intermediate predictions and remaining mistakes are identical to the GRU version, but the final model now returns its answer at the requested loop. That makes the distinction between executing correctly and knowing when to stop much more concrete than it was in the earlier attempts.

The simpler controller also comes with a lot of structure supplied by me. I chose a digit-by-digit reader, a scalar memory and an affine update, then supervised the remaining work directly. It learned the coefficients, but I gave it a form suited to counting. This is a useful solution to a task with a known completion rule. A general way to judge whether reasoning is complete would need more than that. It will stop on time even when the executor is wrong.

So I think the original experiment worked within a fairly specific scope: a small model trained on short graph paths can keep executing them for much longer, with one loop corresponding to one graph transition on the successful trajectories. The 26-state cycles, fixed prompt format and separate timer all matter to that conclusion. The successful executor was trained with one seed; testing graphs from three generation seeds does not tell me how reliably another training run would reproduce it. The next question is how much of this carries over once those conveniences are removed.

What Next?

There are a few things I would like to try next. These are follow-up experiments, rather than things this benchmark already answers.

Find out which changes mattered

Several changes went into the successful executor at once. I would start by comparing runs with and without the requested count in the executor’s prompt, keeping the rest of the recipe the same. Similar comparisons could test the bridge, full training of R, direct supervision and cyclic training data. That would help explain which changes were needed to keep execution working beyond the training horizon.

Make the graph task harder

Two-letter node names would let us go beyond 26 states and test much longer paths without necessarily revisiting a node. Another option is to give each node multiple outgoing edges and use an extra instruction, such as an edge color, to choose the transition. I would also vary the prompt format and rule order to check how much the current result depends on the exact presentation. These would test more than just how long the timer can count.

See whether mistakes can actually be repaired

Right now, another loop means another graph transition, so simply running for longer after an error does not necessarily repair the answer we wanted. I would like to test a version with a clear terminal state, where the target stops changing once the task is complete. Then we could ask whether extra loops fix wrong answers while preserving correct ones. That would be a better starting point for a controller that decides how much computation is useful, instead of only counting a supplied number of steps.

Try another procedure, and measure the cost

Finally, I would like to see whether the recurrent executor can help with another small algorithmic task, such as running a finite-state machine or applying a sequence of symbolic updates. I would test transfer separately from training a new model from scratch. Alongside that, I would measure latency and memory at matched task quality, including the readouts and controller. A shared set of weights is useful, but it does not by itself tell us whether the full system is cheaper to run.
