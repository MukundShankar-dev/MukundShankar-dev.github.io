June 2026 – Present

DexVision

I want to build a robot that can take a request like “put this part on the inspection pad and press Start,” then carry it out using a small set of reusable skills. The eventual LLM orchestrator will choose which skills to call and with what parameters. The skills themselves need to work first.

I started with something much smaller: opening a webcam and making a simulated hand follow mine. This is the development log from there—what I implemented, what broke when I tried it, and what I changed. The first four phases below are reconstructed from my checkpoint notes, written up on September 8, 2026.

Phase 1 · June 2026

Camera input, hand tracking, and teleoperation

The first goal was basic teleoperation: move my hand in front of a camera and have a simulated hand follow it. I built the camera, tracking, feature extraction, and simulation checks separately before connecting them. That made it possible to tell which part was wrong when the combined system behaved badly.

Opening the camera and checking the frame rate

Checkpoints 1.0–1.1

I started with a Python health check for NumPy, OpenCV, MediaPipe, and MuJoCo. Then I wrapped OpenCV's cv2.VideoCapture in a small camera class with configurable camera ID and resolution, a frame-read method, and a clean shutdown. The first app simply opened the feed, displayed FPS, and exited on q. The live check ran at about 30 FPS.

At this point there was no hand detection or robot. I wanted to establish that the camera could deliver frames consistently and that a missing device produced a useful error. The automated camera tests used a mock frame source so they could run without opening a webcam.

Adding MediaPipe hand landmarks

Checkpoint 1.2

Hand tracking uses MediaPipe Hands, with a Tasks Hand Landmarker backend for MediaPipe installations that no longer expose the older Hands API. The Tasks path loads the local hand_landmarker.task model and processes timestamped frames in video mode. OpenCV provides BGR frames, so the tracker converts them to RGB first.

The result is 21 hand landmarks, plus handedness and its confidence score. I drew the points and skeleton connections over the camera feed and checked an open palm, a fist, fast movement, and what happened when the hand left the frame. Missing detections return an explicit no-hand result rather than leaving downstream code to interpret an incomplete landmark array.

The left/right labels needed correcting. MediaPipe's handedness convention assumes a selfie-mirrored image, while the normal OpenCV input was unmirrored. I flipped the labels for that input and kept an option for cameras that already supply mirrored frames. I then checked both hands against the displayed labels.

Turning landmarks into finger controls

Checkpoint 1.3

I did not train a separate model to estimate finger controls. I used geometry computed from the landmarks: a normalized curl value for each finger, thumb–index pinch distance, and palm-orientation proxies. Curl ran from zero for an open finger to one for a closed finger. Live bars next to the camera image made those values inspectable before they drove anything.

The first checks were simple: an open hand should produce low curls, a fist should produce high curls, and pointing should leave the index open while the other fingers closed. Those broad poses were enough to get the first feature extractor running. They were not enough to catch how much one finger's value could change when the surrounding hand pose changed; that became obvious during the one-finger robot test.

Reducing jitter before sending commands

Checkpoint 1.4; revisited after 1.3B

The raw values fluctuated between frames, which would turn into choppy joint motion. I added an exponential moving average and displayed raw and smoothed values together. Each update blends the new measurement with the previous smoothed value: s = α × x + (1 − α) × s_previous. A smaller alpha reduces jitter but also makes the response lag.

The smoother holds the last stable controls when confidence drops; it can also be configured to decay toward a neutral pose. Tests covered noisy input, a sudden step change, and missing values. The implementation stayed with the EMA. The One Euro Filter was listed as a possible later alternative, but was not used here. After the finger-feature rewrite, I smoothed extension and derived bend from that smoothed value.

Checking the simulator without the camera

Checkpoints 1.5–1.9

I first loaded a minimal MuJoCo scene with a floor and a cube and checked that it could reset and step. Next came a simple hand model: discover its joints and actuators, drive one index joint with a periodic command, then play configured open, fist, point, pinch, peace, and relaxed poses.

That simple hand became a debug model. Before recording any demonstrations, I selected the right Shadow Hand E3M5 from Google DeepMind's MuJoCo Menagerie as the final model. Its joint names, limits, and 20 actuators would define the saved action format. Some finger joints are coupled through tendon actuators, so the mapping could not assume one independent actuator for every visible joint.

The first retargeter interpolated configured open/closed robot targets from the human finger controls, with per-finger scaling and limit clipping. “Retargeting” here means translating a human hand measurement into commands for a hand with different joints and proportions. I checked the scripted robot gestures before introducing live camera input.

The index finger test exposed a feature problem

Checkpoint 1.10 → reopened as 1.3B

I connected only my index finger to the robot index finger and held every other robot finger open. The robot followed the reported index command, and the other robot fingers stayed still. But a similar-looking human index pose could produce a very different command depending on what my other fingers were doing. Pointing gave a value around 0.17; a fist gave roughly 0.70–0.78; changing the surrounding fingers could push the value into the curled range even without the intended index movement.

That separated two possible causes. The retargeter was not leaking the command into other robot fingers. The feature extractor was producing a coupled or unstable input. I reopened feature extraction rather than changing robot joint limits to compensate.

The replacement gives each long finger its own MCP/PIP/DIP/tip chain: the base knuckle, two finger joints, and fingertip. Curl is computed from local joint bend angles. Extension measures the tip's displacement from its own base along the palm's forward axis, normalized by the finger-chain length. The palm frame comes from the wrist and index, middle, and pinky knuckles. Thumb geometry is handled separately using its CMC/MCP/IP/tip chain and an opposition measure.

This improved independence, but the raw curl bars still did not match the live pose as intuitively as extension did. For the four long fingers I changed the actual robot-control signal to bend = clamp(1 − extension, 0, 1). Raw curl remained visible for diagnosis. The thumb retained a more conservative mapping.

I added synthetic checks for each finger raised on its own, a peace sign, partial fists, pinch, and index movement with the other fingers fixed. Then I reran the live feature viewer and the one-finger robot test. The revised bend signal passed manual review on June 11.

Connecting the rest of the hand

Checkpoints 1.11–1.12

With the one-finger path working, I connected all five fingers. Open palm, fist, and pointing worked; pinch and peace were approximate. I checked tracking loss and added the useful diagnostics to the combined demo: landmarks, finger bars, confidence, FPS, and tracking-loss messages. This gave me a working fixed-base hand demo, but the hand still could not move over to an object.

Moving the whole hand was a separate problem

Checkpoint 1.13, initial attempts

Adding base translation and wrist rotation introduced problems that finger-only teleoperation had not exposed. The live app sometimes stopped on a high-velocity simulation guard, and the robot's orientation looked under-rotated. I tried rate-limiting the base target, stronger smoothing, and an orientation offset.

Further trials behaved better with my right hand than my left. Making a fist or rotating my wrist could also push the simulated base down or sideways into a workspace boundary. I tried a wrist-based translation anchor, mirrored the left-hand orientation into the right-hand model's convention, and reset smoothing and calibration state after tracking loss. These changes addressed parts of the behavior, but the combined mapping was still awkward: one axis barely moved, height kept clamping near the floor, and orientation was noisy.

I split the problem back into smaller tests. Translation would be calibrated from the image, depth would use hand scale, and rotation would remain disabled until those controls worked.

Calibrating translation, depth, and rotation one at a time

Checkpoints 1.13A–1.13D

For translation, pressing c captures a comfortable neutral hand pose. Palm-center displacement in the image then maps to robot lateral movement and height. This was easier to inspect than a combined position/orientation mapping, and it kept the hand inside configured workspace limits.

For depth, I used apparent hand size as a monocular proxy: moving closer to the camera makes the hand larger, moving away makes it smaller. Calibration stores the neutral scale; the change drives bounded in/out motion. Smoothing and a deadband stop small scale fluctuations from moving the hand continually. This is a relative depth control, not metric 3D reconstruction.

Rotation also became relative to calibration. I stored the human palm orientation and robot orientation together, then applied the change from that reference. I tested roll alone before enabling pitch and yaw, with configurable axis signs, remapping, smoothing, and rate limits. The initial 45-degree limits were too restrictive for approach poses, so the final pass widened roll/yaw to 120 degrees and pitch to 110 degrees.

By the end of phase 1, translation, depth, wrist rotation, and fingers worked together in the live demo. Depth was still approximate, orientation still depended on camera viewpoint, and the thumb was less expressive than the other fingers. The next step was to record this behavior and see whether it survived replay.

Phase 2 · June–September 2026

Recording demonstrations—and getting them to replay

A live demo disappears when the window closes. To use it for learning, I needed to save enough information to reconstruct both the commands and the task. Phase 2 started with recording free-space gestures, then introduced reach, button press, and cube push one at a time. Cube push took considerably more debugging than the checklist initially suggested.

Deciding what an episode contains

Checkpoints 2.0–2.3

I first outlined resettable tasks with explicit targets and success conditions. The episode format then recorded the full phase 1 action: three base-position values, a four-value orientation quaternion, and the finger/wrist actuator targets. It also saved robot positions and velocities, landmarks and extracted features, tracking quality, timestamps, and the configuration used for that run. Object and task states were added when a task needed them.

The recorder writes metadata and NumPy arrays with matching time dimensions. Validation checks shapes, missing fields, finite values, and timestamp order. A runbook defined how to name attempts and inspect them. Replay loads the saved scene and applies the recorded actions, with headless and viewer modes and adjustable playback speed.

Later I made the observation layouts executable: each field declares its array, columns or named joints, shape, units, and coordinate frame. That lets the loader reconstruct a field by name. Existing gesture recordings kept an explicit compatibility path rather than being silently reinterpreted under a new layout.

The first recordings: calibration, pinch, and shutdown

Checkpoints 2.4–2.4C

The first dataset contained open palm, fist, point, pinch, peace sign, and wave. Recording was changed to wait until c successfully calibrated the hand, so setup motion was not saved as part of the intended gesture. Static poses were held for roughly three to five seconds; wave was the moving example.

Pinch exposed another mismatch: the index could curl while the thumb stayed open. I added a pinch overlay to the retargeting path and a “Pinch close” bar so I could tell whether the app actually saw thumb–index closure. The goal at this stage was a recognizable approximate pinch, not exact fingertip contact.

I also checked that q closed both windows and returned the terminal prompt. Printing “Saved demo” was not sufficient if the macOS viewer kept the process alive. By the July 18 audit there were 60 valid recordings, ten per gesture, and all 60 completed headless replay. One pinch clip included extra open-hand transition footage but retained an uninterrupted 3.97-second pinch, which I documented when keeping it.

Before collecting object tasks, I added the clean-environment setup, dependencies, linting, and generated-file exclusions. The raw local recordings stayed intact while the repository became reproducible from a fresh checkout.

Reach: separating task success from data quality

Checkpoints 2.5–2.7C

I built a task board with a deterministic reset and selectable reach targets, then recorded a five-demo pilot over at least three targets. Each episode saved the selected target and initial state. I added success recomputation from saved state so I could compare the operator label with what the trajectory actually did.

Next came quality filters for tracking loss, low confidence, feature jitter, action jerk, workspace saturation, joint-limit hits, and task failure. These answer a different question from “did it reach the target?” A successful attempt can still contain poor control data. Reports kept both the result and the rejection reason without changing the raw recording.

The balanced collection helper chose among targets with the fewest clean successes. The final reach set had 76 raw episodes: 69 recomputed successes, but only 55 quality-passed successes. Those 55 were split 18 left, 18 center, and 19 right. Two interpolated target positions were reserved for later rollout evaluation before training began.

Button press: checking the intended button

Checkpoints 2.7D–2.7E

The board gained three passive spring-return buttons with slide joints. A task could specify the button and desired press depth. The first five demonstrations covered all three buttons and depths from 10 to 14 mm, then went through the same replay, label-recomputation, and quality pipeline.

To make selection unambiguous, the target button was bright green and the others dark gray. Unrelated reach fixtures were hidden and non-colliding during button recording and replay. An audit checked that the selected button was the primary press, rather than counting any nearby contact as success. All five pilot recordings passed.

Cube push: responsive commands, sluggish physics

Checkpoints 2.7F–2.7G · July 19 onward

The push task used a free-moving cube, named start lanes and targets, and a success check based on planar distance and dwell time. The first usable scene needed the wall and unrelated fixtures hidden, and the physical hand and its commanded base target reset together behind the cube.

The first replacement trial had excellent tracking, but only 5.6 cm of forward command range over 31.7 seconds and pushed away from the target. I adjusted translation/depth gains, smoothing, deadband, and the per-frame movement cap. A later trial still felt delayed even though the command itself changed promptly.

The recorded state exposed the cause: the physical base trailed its target by 3.3 cm on average and 7.4 cm at the 95th percentile. The loop advanced MuJoCo by two 2 ms steps for each camera frame, or 4 ms of simulated time per roughly 33 ms of real time. I changed cube recording to at least 17 simulation steps per frame at 30 Hz and saved that cadence in the metadata. A headless regression reduced the final following error from about 2.5 cm to 2 mm.

Fixing the palm pose, then finding a preset that undid it

Further 2.7G trials

After the timing fix, the hand responded, but the cube moved 27 cm and rose more than 10 cm. That was a scoop, not the delayed response I had been diagnosing. My real palm was upright while the simulated palm was horizontal, making height and push direction hard to interpret.

I tried an upright reset and damped the motion. The next trial had only 2.3 mm mean following error, but the cube moved backward. The robot fingers pointed along the push axis when the palm normal needed to. I changed the reset to a camera-facing, fingers-up palm and mapped depth along that palm normal.

Another recording exposed two orientation bugs. The reset quaternion actually presented the back of the hand to the cube, and the general full-control preset re-enabled live wrist orientation after the task had disabled it. The hand rotated out of view after about 1.2 seconds. I corrected the reset and forced push-task orientation off after applying the preset, then saved the effective enable flags so replay could use what had really run.

Reducing push to a motion I could collect reliably

Further 2.7G trials

A fixed commanded orientation still did not stop physical deflection. The visible forearm and wrist crossed the tabletop at reset, and camera up/down motion spanned 15 cm of commanded height. Table contact could knock the hand sideways despite the fixed target quaternion. That trial had 3.6 cm mean following error and 11.6 cm at the 95th percentile.

I hid and disabled the below-table support geometry, fixed height at a stable pushing plane, and narrowed the forward and lateral workspace. Named start/target lanes made the task a straight planar push. The next clean reference ended 2.72 cm from the target with little cube lift, but it had no operator success label: push had been omitted from the shared label prompt. I fixed the prompt before counting accepted pilots.

Two later attempts reached the target and agreed with their operator labels but failed the workspace quality gate. Lateral commands spent 32.7%, then 12.8%, of their frames at the boundary; the allowed maximum was 10%. Centering the lateral workspace helped but did not fully solve it. Since each start and target were already aligned, I fixed lateral position too. Only bounded forward/backward input remained active during the push.

This deliberately reduced what the demonstration represented. The final pilot showed controlled straight pushes in three lanes, with height, orientation, and lateral position fixed. It did not show general manipulation of a cube.

Five successful pushes still needed coverage—and a replay fix

Completion of 2.7G · September 2

The first batch of five clean successes all used the left target. I kept three and replaced the redundant examples with center and right recordings. The final five had full hand detection, roughly 1.3–2.3 mm mean base-following error, less than 1 mm maximum cube lift, and final distances around 2–3 cm.

Verification then caught a separate replay bug: the replay command still defaulted to one physics step per action, even though these recordings used 17. I made replay read the saved cadence, with an explicit override and a one-step fallback for legacy data. Only after all five replays showed the correct start, target, and final behavior did the pilot close.

Scaling the narrow tasks and exporting their interfaces

Checkpoints 2.7H–2.7J

The button selector balanced collection across nine button/depth combinations and produced 55 clean episodes. Push collection reached 101 clean episodes, distributed 33/34/34 across the left, center, and right lanes. Each retained episode had replay, recomputed labels, and quality checks. Interpolated button depths and cube start/target conditions stayed held out for learning evaluation.

I also exported preliminary skill metadata: parameters, units, frames, preconditions, success/failure conditions, and timeouts. These were interface stubs with no learned policy attached. They gave later training and orchestration a defined task to implement.

Did a more complex retargeter help?

Checkpoints 2.8–2.10B

I added two alternatives to the original curl/bend mapping. The fingertip baseline transforms landmarks into a palm-local frame, normalizes by palm width, and uses a simple geometric mapping to bounded robot targets. The optimization version solves for five normalized finger controls, minimizing fingertip error with actuator-limit and previous-solution smoothness terms. It uses SciPy L-BFGS-B when available and a projected-gradient fallback otherwise.

I first benchmarked ten push episodes, then expanded to all 101 episodes and 7,176 frames. Each method received the same saved human inputs and base actions, and I replayed its substituted finger commands. The full comparison added 2,000 episode-bootstrap resamples and measurements of fingertip distance and contact in MuJoCo.

Curl and optimization both achieved 87.1% replay success; the fingertip baseline achieved 83.2%, with overlapping confidence intervals. Optimization lowered the surrogate fingertip error but did not beat curl's task success, speed, or smoothness. The original base trajectories had been collected under curl control, so this was a comparison on those trajectories, not independent live collection under each retargeter.

Freezing the inputs to the first learning experiment

Checkpoint 2.11

I packaged the historical data and reports with an immutable manifest and checksums. The learning sets were now 55 reach, 55 button, and 101 push successes. For reach, I froze an 80/20 goal-stratified split by whole episode, training-only normalization, and 35 rollout scenarios: 21 using training targets and 14 using held-out targets, with fixed one-centimeter start perturbations.

The old recordings did not contain genuine session IDs, so they could not support a cross-session claim. They were still enough to ask the next question: could a small model learn useful behavior from these saved states and commands?

Phase 3 · September 3, 2026

Training the first policies and finding out why they failed

Phase 2's checks showed that demonstrations could be recorded, validated, and replayed. They did not show that a learned policy could reproduce them. I kept this phase small: simulator state as input, a goal-conditioned MLP, and behavior cloning, which trains the model to predict the demonstrated action.

Loading data, defining the model, and training on CPU

Checkpoints 3.0–3.3

I separated this feasibility study from the larger dataset and skill-training phases. The loader resolved observations through the saved layouts and kept complete episodes together. The frozen reach split contained 43 training and 12 validation episodes; normalization used only the training portion.

The model took robot/task state and the typed goal and predicted the full 27-value action: base position, quaternion orientation, and 20 actuator targets. I used a small MLP with two 128-unit hidden layers. Before running the real experiment, I checked output shapes, save/load consistency, and whether the training loop could overfit a tiny dataset.

The real reach run trained for 100 epochs on CPU. I saved the loss history, optimizer and model state, seed, normalization statistics, and data/configuration digests. That made it possible to repeat the training run and verify which checkpoint an evaluation actually used.

The first rollout was partly successful and still failed the test

Checkpoint 3.4

A rollout closes the loop: the model predicts an action, MuJoCo executes it, and the resulting state becomes the next input. That is different from predicting actions on a saved trajectory where the next state is already supplied.

The first reach checkpoint completed 17 of 35 frozen scenarios. Success was 38.1% on training targets and 64.3% on held-out targets. The other 18 runs ended at joint or workspace limits, so the policy did not pass the predefined acceptance criteria. I kept the failed trajectories and their terminal reasons alongside the successful ones.

I had evaluated the wrong checkpoint

Checkpoints 3.5A–3.5B

The first evaluator used epoch 100, even though validation loss had been lowest at epoch 15. I changed training to save separate last and best-validation checkpoints and select the earliest epoch in a tie. Then I repeated reach with the same dataset, split, seed, model, training budget, and rollout conditions.

The corrected selection made the rollout result worse: zero successes, with 20 workspace-limit and 15 joint-limit failures. Lower validation loss had not meant better closed-loop control. Repeated fixed-seed training reproduced the checkpoint hashes, so I preserved both evaluations rather than dismissing the difference as a new random run.

I also froze button and push rollout protocols before training those tasks. The button model selected epoch 17 and push selected epoch 97. Both failed every rollout at the first control step because of joint-limit violations.

Checking the action representation before changing the model

Checkpoint 3.6

I compared full-action, base-only, finger-only, and fixed-goal variants under the same splits, seeds, model size, and evaluation conditions. Any action fields omitted by an experiment held their prior applied values. This let me examine the effect of controlling different parts of the hand without changing the stored demonstrations.

Reach and push still had no successful diagnostic variant. Button improved to 33.3% success with base-only control, while a fixed-training-mean goal variant reached 19.0%. Both still had safety violations. Action grouping clearly affected the outcome, but none of those changes produced a qualified policy.

I also tested whether quality filtering had removed useful reach examples by expanding from 55 clean successes to all 69 recomputed successes. It did not rescue the result. Button and push had no equivalent broader-success set, so there was no matching comparison to run for those tasks.

Why I did not add a GRU yet

Checkpoint 3.7

The plan allowed a short-history model if the results showed that the current state was ambiguous or that errors accumulated over time. But the full button and push policies stopped after one control step. Those runs showed an immediate control/safety problem; they did not establish a need for memory.

I left the GRU unimplemented. That did not prove a temporal model could never help. It meant I had not measured the failure that would justify adding it. Missing recovery examples and compounding error remained possible explanations to investigate, rather than conclusions drawn from these runs.

What carried forward into phase 4

Checkpoint 3.8

The loading, training, checkpointing, and frozen-evaluation loop worked reproducibly. None of the tested full-action policies was ready to use as a skill. The next phase needed a better-defined control interface and broader task data: real session ownership, explicit task phases, prior applied actions, safety records, and object/goal variation.

That still left a practical question unanswered: how would I collect those more complicated demonstrations? Phase 4 initially tried extending the live hand-control approach. The contact-task pilot was where that assumption broke down.

Phase 4 · September 3–8, 2026 · Through checkpoint 4.5A

A workcell, a failed control pilot, and scripted experts

The earlier tasks each had a narrow setup. For reusable skills, I needed a common scene where an object's state at the end of one task could become the starting point for another. I specified a tabletop workcell with blocks, cylinders, and pucks, two return bins, an inspection pad, two setup slots, and a Start button.

Defining the scene—and fixing what the viewer revealed

Checkpoints 4.0–4.1

The first plan defined five skills: reach, pick, place-held-object, push, and press. Each got initial-state requirements and a measurable end condition. The world-state format included named entities, pose and velocity, support/contact/held relations, timestamps, and units. I also assigned collection conditions to training, validation, or test sessions before recording them.

The scene passed automated checks, but the first interactive viewer was locked to a fixed camera and exited after 1,200 steps. I changed it to a movable overview with reset, seed, pause, and label controls. Colors alone were ambiguous; after adding labels, I found MuJoCo hid the site group containing their anchors by default. Moving the workcell labels into a visible group fixed that.

The return bins then appeared left/right reversed, and randomized objects could obscure the setup slots. Camera adjustments alone did not fix the bin names because the target coordinates themselves encoded the opposite ordering. An initial screen-space check also had its horizontal-vector sign reversed. I corrected target coordinates, scene bodies, and the check together. Deterministic spawn lanes and clearance tests kept objects off the slot markers. The resulting viewer passed manual review on September 3.

Recording phases and the actions that were actually applied

Checkpoint 4.2

The new format distinguishes requested, commanded, and applied actions, plus prior actions and per-field clipping or rejection reasons. That matters when a controller asks for one thing and a safety limit changes it. A learner should not treat the original request as though the robot executed it unchanged.

I added session manifests, unique episode allocation, and append-only writes. Task phases such as approach, acquire, lift, transport, release, and settle can be computed from current and previous state, without looking at future frames. A complete pick/place recording can then provide compatible reach, pick, and place segments while still counting as one recorded episode.

Trying to collect the new tasks with the old controls

The original 4.3 pilot · September 4

The first reach attempt put the forearm root on the board as if it were the palm's control point. I corrected the planning point, reset the physical hand at the commanded pose, and kept the forearm outside the work area. The next attempt showed that imitating robot orientation with my real hand was still awkward, so I locked robot orientation and used an upright, webcam-facing palm as a translation control.

A later reach entered the target tolerance for 36 frames but moved two neighboring objects by about 7 cm. The approach marker was too low. Raising it to a collision-free pre-grasp pose addressed that. Then the new recorder repeated a timing mistake from phase 2: one 2 ms step per camera frame made motion roughly 17 times slower than real time. I restored the 17-step cadence.

Absolute image-to-position mapping still required moving near the edge of the camera frame, and those attempts disturbed the scene. I replaced gain tuning with centered nonlinear Cartesian rate control, where displacement from neutral controls motion rate, and added a high transit path with descent allowed near the target. Separate visual cues showed the selected object and the desired palm position.

Four retained trials then tested reach, pick/place, push, and press. Reach worked, ending about 1.62 cm from its target with roughly 2.1 mm scene disturbance. Pick/place moved the intended block and a neighbor without grasping. Push did not move its selected block. Button press never reached a usable approach range and recorded zero depth. I judged only reach usable.

That was the point where I changed the collection strategy. The phase 1 camera control could make a good teleoperation demo, and phase 2 could collect heavily constrained pushes, but it was not producing the contact demonstrations this workcell needed. I kept those experiments as history and moved active collection to deterministic controllers using simulator state.

Scripted reach first, then button press

Checkpoints 4.3A–4.3B

I gave each scripted expert a reset/step interface and reused the existing recorder. Reach plans around the palm/grasp site: rise to a safe height, travel horizontally, enter a protected approach corridor, then descend. Candidate motion is executed in a scratch copy of MuJoCo state first to check workspace limits, joint limits, collisions, and neighbor movement.

Five randomized reaches passed, but the first visible review was misleadingly choppy because playback was set to 0.1×—about three displayed poses per second from a 30 Hz recording. The target cage also started at the object's center instead of enclosing it. I corrected the cage and verified the replay.

The button expert kept posture and orientation fixed, moved along the button normal, held the required depth, and retracted until release. The button needed to be mounted inside the usable workspace, with recovery travel beyond the largest task depth. Five randomized resets then recorded and replayed successfully without unintended contact or safety interventions.

Push and grasp needed their own physical checks

Checkpoints 4.3C–4.3D

Push derives its forward axis from the object's start and goal. After approaching from behind, it fixes height, orientation, and fingers and moves along that axis. A cuboid push needed remediation so that sliding, not tipping into the target, counted as success. I required table support, no more than ten degrees of tilt, and a stable result after retraction instead of latching a momentary target hit.

For grasp-and-lift, I used separate object-relative templates for cuboids, cylinders, and flat pucks. Each specifies a grasp offset, wrist pose, open/closed hand targets, and a scalar grasp-synergy control. To isolate the grasp physics from the clutter problem the pilot had already shown, standalone trials kept the selected object in place and parked non-target objects on the lower floor.

Finishing the controller's “lift” phase was not enough to call it a pick. The object had to leave table support, rise at least 4 cm, be held through contact with at least two hand bodies, and remain below the speed threshold for ten samples. Three seeds per object family passed. In visible review, though, the cuboid rotated substantially while held. That did not violate the initial lift metric, but it would matter when placing the object with a useful orientation.

The grasp that lifted the block did not place it well

Checkpoints 4.3E–4.3F

The first complete sequence added transport, descent, release, settling, and retraction. Visual review rejected the original top-down grasp because the cuboid yawed about 24 degrees in the hand. I changed the shared grasp to a side-on wrist pose and added an explicit rotation-only orientation hold during lift and transport. Translation and release remained governed by the simulation.

This is a simplifying constraint in the expert, not learned orientation control. Round objects also needed task-local contact and rolling-resistance settings to grasp and settle consistently. Those changes applied to pick and pick/place so they did not silently alter the already-tested push behavior.

Ten complete sequences across the three object families then recorded, recomputed, and replayed successfully. I followed that with a shared audit over two resets each for reach, button, push, grasp-and-lift, and complete pick/place. All ten passed, and I reviewed one visible replay per skill before moving on.

A smaller learned interface—and another joint-limit bug

Checkpoint 4.3G · September 5

Before collecting a large dataset, I wanted to check whether this formulation was learnable. I collected 20 scripted button episodes with a 14/3/3 whole-session split and trained one MLP with two 64-unit tanh layers. It observed task-relative geometry, button state, velocity, phase, and the previous applied delta, and predicted only task-frame dx, dy, dz. A deterministic adapter supplied the fixed posture and orientation.

The first varied-reset evaluation failed ten of twenty rollouts. Contact pushed the middle finger joint rh_MFJ1 past its limit. Giving the fixed posture a small interior margin removed that failure, then three right-offset cases exposed the same problem on rh_FFJ1. A one-percent index margin resolved those cases too.

The resulting pilot completed 20/20 held-out press-and-release rollouts without safety or contact violations. The dataset stayed at 20 episodes and the model recipe stayed the same; the fixes were in the control posture. The held-out trials did inform those repairs, so this is development-pilot evidence. Full skill qualification is still later work.

The push model needed the expert to remain in control

Checkpoint 4.3H

I reused the small-model convention and 20-episode split for push. Predicting the entire motion delta failed 0/20: approach errors accumulated until the hand reached a workspace boundary. I kept the scripted controller responsible for the nominal path and contact behavior and trained the model on a small tracking residual instead, bounded to 1 mm and 0.5 mm along the contact axis.

The combined controller completed 20/20 held-out cuboid and puck resets. That result shows the residual interface can run successfully alongside the expert. It does not show that the residual improves on the expert alone; that needs a zero-residual comparison.

Copied-state checks also showed that some proposed right-bin push routes crossed the fixture region, and a puck approach waypoint left the workspace. I removed those unsupported conditions from this controller's collection scope rather than treating them as collectable because they appeared in the original plan.

Freezing coverage and collecting the core tasks

Checkpoints 4.3I–4.4 · September 5–6

The initial plan had estimated 250–350 episodes. After the pilots, I froze a smaller 114-episode integration matrix, with 74 rows describing skill/object/goal or failure conditions and their split ownership. The push subset retained twelve qualified conditions and documented the excluded ones. The source mix was revised again before core collection so all required nominal demonstrations came from scripted experts.

The first completed haul contained 60 required episodes: twenty reach, twenty push, and twenty press, covering all 32 core cells. Training and validation data were frozen before the fourteen test-owned episodes were recorded. Four push test cells used seeds already qualified in the earlier pilot because the generic seed sequence failed the copied-state workspace check. That restriction remains part of what this collection covers.

The pick/place anchor uncovered geometry and replay issues again

Checkpoint 4.5A · September 8

The next haul targeted 42 complete pick/place episodes across thirty split-owned cells. The first test audit accepted only four of eighteen assignments. The earlier templates did not transfer cleanly to the larger cuboid, taller cylinder, and heavier puck.

I introduced object-specific grasp points and placement-center corrections in a new version. Return-bin walls became visual guides, and validation, recording, and replay were made to use the same internal orientation-hold cadence. The earlier failed attempts remained preserved; the corrected runs did not replace their history.

The revised anchor passed all 42 episodes. Each could be replayed, have its task result recomputed, and yield compatible reach, pick, and place segments. What I still need to do in this phase

Planned checkpoints 4.5B–4.9

The anchor verifies the collection path and coverage, but it is too narrow to establish that the data is sufficient for learning. The next plan expands each nominal cell to at least sixteen independently seeded accepted episodes: 992 nominal episodes in total, including the existing anchors. A further 120 failure/correction episodes would bring the planned minimum to 1,112.

I plan to compare nested training subsets of four, eight, and sixteen episodes per cell using the same recipe and validation rollouts. That should tell me whether performance is still improving with more data and where coverage remains weak. Test data will not decide the collection size.

The remaining checkpoints add separately labeled failures and scripted corrections, aligned rendered images with object labels and poses, split and coverage audits, and a versioned release. Full skill training and visual execution follow that release. The LLM orchestrator still depends on those skills being reliable enough to compose.
